# Verification Plan

This page is the **what** — the properties every layer must prove. The **how** — the unit/integration
split, in-memory port fakes, and the per-provider mock servers that drive the real adapters — lives in
[11-testing](11-testing.md).

**Automated (`pytest` + `pytest-asyncio`; `respx` for the httpx clients; `testcontainers[postgres]` for real-Postgres repository/worker tests):**

- **Domain / persistence**: enum round-trip; `RunState` round-trips through `PydanticJSONB` (save → load → identical model); a `RunState` with unknown/invalid fields fails validation loudly; per-step retry budget; optimistic-concurrency conflict (`StaleRunError`) → executor drops the lost save, another worker re-drives (never clobbers); idempotent double-execution of every step (typed markers skip completed work); terminal failure path (retries exhausted → run `FAILED`, Incident opened, RITM work note, resource record marked `state=FAILED`/`in_progress=False`, **nothing rolled back**).
- **Decoupling / driver**: the `RunExecutor` is invoked with only a `run_id` and loads all state from the run store; a `run_id` for a terminal run is a no-op; a run advances through multiple synchronous steps in one wake-up and, at an async wait/retry, sets `scheduled_at` (deferral is run state, never a transport delay).
- **Workers**: `claim_due` returns runs with `scheduled_at <= now`, skips future/NULL ones, and pushes claimed rows' `scheduled_at` forward by the lease (so a crashed drive re-drives); each `RunWorker` claims one run at a time (`claim_due(1)`) and drives it, backing off a poll interval when nothing is due; concurrent workers (in one daemon or many) never claim the same run twice (`SKIP LOCKED`).
- **Airflow client** (v2, token auth, `verify=False`): authenticates via `/auth/token` and refreshes on 401; `trigger_workflow` posts `dag_run_id`/`conf` (409 → idempotent, 404 → "DAG not found"); `query_run_status` maps `queued/running` → `EngineRunStatus.IN_PROGRESS`; `get_failure` returns a typed `EngineFailure` (failed task + responsible group + message) and an empty `EngineFailure` when no failed task is listed; `get_output` probes the run's task instances for a named XCom and returns its value (or `None` when absent).
- **ServiceNow client**: `open_ticket` orders the catalog item, resolves the RITM from the created Request, tags `correlation_id`, returns RITM `number`+`sys_id` (a same-key retry returns the existing RITM); `close_ticket`/`annotate_ticket` PATCH the RITM (state 3 / work note); `open_incident` builds the documented INC payload and resolves the responsible group via the dict (fallback to the exact name). No ServiceNow vocabulary crosses the port.
- **Project Manager client**: `create_resource` POSTs to `/projects/{id}/project_resources/{type}` with the `Idempotency-Key` header and returns the provider's own record id from the response (`project_resource_id`, or `None` when it carries none); `update_resource` PATCHes by `vendor_id` (a `404` raises `ResourceNotFoundError`); `delete_resource` DELETEs by `vendor_id` (a `404` is treated as already-deleted). Finalize PATCHes `state=READY`/`in_progress=False` — plus the spec's fields on an UPDATE — or, on a DELETE, PATCHes `state=DELETED` and then DELETEs the record (a `ResourceNotFoundError` on that PATCH counts as already deleted). **Confirm the provider actually exposes the DELETE**; the plugin doc lists only Create and Patch.
- **Resource lifecycle state**: every state write carries `state` and `in_progress` (true exactly for `PROVISIONING`/`UPDATING`/`DELETING`), and **no run id**; `configuring_resource` — which runs *before* the approval gate — POSTs a CREATE's record (vendor id = run id, `Idempotency-Key` `{run_id}:configuring_resource`) and stores the record id the provider answers with, or PATCHes an UPDATE/DELETE's record to `UPDATING`/`DELETING`; a rejection deletes a CREATE's record or returns an UPDATE/DELETE's to `READY`; a failure marks `FAILED`; none of these fire for an automation run, a run that never configured its resource, or one already finalized; a PM error never blocks the incident and a ticket-system error never blocks the record update.
- **Latest run for a resource**: `GET /api/v1/workflow-runs/latest?resource_id=…` answers the most recent run for that record (by `created_at`) as a trimmed `ResourceRunSummary` — never the internal `run_state` — and `404`s when the record has no runs; the route resolves ahead of `/workflow-runs/{run_id}`, whose UUID path parameter would otherwise reject `latest`; the repository query is keyed on `run_state.resource.resource_id`, so records sharing a `vendor_id` (one per region/environment) never answer for each other.
- **Engine-reported vendor id**: on engine success `RunEngineStep` reads the `final_vendor_id` output and, if present, records it in `state.step_results[RUN_ENGINE]`; `FinalizeResourceStep` then re-keys the record to it as it PATCHes (for a CREATE, off the run-id placeholder) and updates `run_state.resource.vendor_id` to match, so `?vendor_id=<real vendor id>` finds the run, leaving the record where it is when the run produced no output (reading the output is best-effort — a fetch error never fails a succeeded run).
- **Failure model**: a permanently-failed step opens an Incident to the responsible group (engine failure → group from `get_failure`; otherwise `cloudio`) and adds a work note to the RITM, then marks the resource record `FAILED`; a rejection ends the run `REJECTED` with no Incident and releases the record; escalation errors never crash the worker.
- **Workflow registry / trigger**: register a workflow, then trigger by `workflow_identifier` → `WorkflowRun` built with the mapped `ResolvedWorkflow` snapshot and `scheduled_at=now`; unknown identifier → 404 (`UnknownWorkflowError`); resource workflow without `resource` → 422 (`ResourceParamsRequired`); an `update`/`delete` without `resource.vendor_id` → 422 (`ResourceVendorIdRequired`), and without `resource.resource_id` → 422 (`ResourceIdRequired`); malformed `ResourceSpec` → 422 from Pydantic at the boundary; resource flows begin with `creating_ticket` (automation flows attach to the caller's RITM and begin with `running_engine`).
- **Static gates**: `uv run ruff check` clean; `uv run mypy` (strict) clean — the typing rules are enforced, not aspirational.

**Integration / manual:**
- Start ≥2 daemons (each claims + drives); confirm no `run_id` is processed by two workers concurrently and no due run is driven twice (`SKIP LOCKED` + the `version` check).
- Trigger a real Airflow DAG end-to-end; kill a worker mid-drive and confirm another worker re-drives the run once its `scheduled_at` lease expires, resuming from the correct step (idempotent replay via the typed state markers).
- Exercise the retention/purge job (terminal `workflow_runs` rows).
- Against the real Project Manager: confirm it accepts and returns `state` and `in_progress` on create and PATCH, that its **create response carries the record's `project_resource_id`** (the key the latest-run endpoint is queried by), and that it answers `404` to a PATCH of a missing record (see [11-testing](11-testing.md#verifying-against-the-real-project-manager)).
