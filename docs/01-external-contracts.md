# User Review Required

> [!IMPORTANT]
> **Contracts on external services:**
> 1. **Idempotency keys.** Run delivery is at-least-once (a worker can crash mid-call, or a run can be re-driven by another worker after its lease expires during a slow call). Every side-effecting external call carries an idempotency key, in one of two shapes: `(run_id, step)` — stable across re-drives *and* retries — for ticket and resource creation, and `(run_id, running_engine, attempt)` — attempt-scoped — for the engine trigger, so that a retry starts a fresh engine run rather than re-attaching to the failed one. **Airflow** sends the attempt-scoped key as the `dag_run_id` (a duplicate returns HTTP 409, treated as "already triggered"). **ServiceNow** Create Request has no native idempotency key, so the orchestrator looks up an RITM tagged with `correlation_id == key` before ordering and tags the new RITM after (residual window: a crash between ordering and tagging leaves the RITM existing but untagged, so the pre-order lookup cannot find it and the next attempt double-orders — note that with compensation removed a double-ordered RITM is *not* auto-annotated, so this window is now operator-visible only). **Project Manager** Create Resource is effectively keyed by the caller-supplied `vendor_id` (plus an orchestrator-added `Idempotency-Key` header). *Confirm each service actually honors these.*
> 2. **Completion signal — polling, with callbacks as a wake-early optimization.** The orchestrator always polls (`query_run_status`, `get_approval_status`): async waits set the run's `scheduled_at` a poll interval into the future, and a worker re-drives the run when due. **Callbacks co-exist with polling** to cut that wait: an external system (the ticket system on an approval change, the engine on run completion) POSTs to `/api/v1/callbacks/{ticket-approval,engine-run}` with only a *neutral reference* (`ticket_id` / `engine_run_id`), and the orchestrator resolves the waiting run and sets `scheduled_at=now` (`runs.wake(...)`) so it re-polls immediately. The callback **never carries a status** and is not a run-store writer of state — the re-driven poll step still reads the authoritative external status, so polling remains the source of truth and a lost/duplicate/out-of-order callback is harmless (the run advances on its next poll anyway). Auth is **network-trust** (no HMAC/token); the endpoints are idempotent (a stale or unknown reference is a no-op, `woken=0`). *The ServiceNow side (a business rule POSTing `ticket_id` on approval) is configured in ServiceNow; the Airflow side is a best-effort `on_success/on_failure_callback` on the DAG.*
> 3. **Failure model.** On a step's permanent failure the orchestrator opens a ServiceNow **Incident** to the responsible group (from Airflow *Get Task Exceptions* for DAG failures, else the default `cloudio` team), adds a work note to the corresponding RITM, and terminates the run as `FAILED`. Transient errors are retried first (per-step backoff, scheduled via `scheduled_at`); the Incident opens once retries are exhausted. **There is no rollback** — a resource created before a later step failed is left with `in_progress=False` for operator follow-up. *If you want DAG failures to skip retries and escalate immediately, set the run's `max_retries=0`.*
