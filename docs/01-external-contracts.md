# User Review Required

> [!IMPORTANT]
> **Contracts on external services:**
> 1. **Idempotency keys.** Run delivery is at-least-once (a worker can crash mid-call, or a run can be re-driven by another worker after its lease expires during a slow call). Every side-effecting external call carries an idempotency key, in one of two shapes: `(run_id, step)` — stable across re-drives *and* retries — for ticket and resource creation, and `(run_id, running_engine, attempt)` — attempt-scoped — for the engine trigger, so that a retry starts a fresh engine run rather than re-attaching to the failed one. **Airflow** sends the attempt-scoped key as the `dag_run_id` (a duplicate returns HTTP 409, treated as "already triggered"). **ServiceNow** Create Request has no native idempotency key, so the orchestrator looks up an RITM tagged with `correlation_id == key` before ordering and tags the new RITM after (residual window: a crash between ordering and tagging leaves the RITM existing but untagged, so the pre-order lookup cannot find it and the next attempt double-orders — note that with compensation removed a double-ordered RITM is *not* auto-annotated, so this window is now operator-visible only). **Project Manager** Create Resource is effectively keyed by the caller-supplied `vendor_id` (plus an orchestrator-added `Idempotency-Key` header). *Confirm each service actually honors these.*
> 2. **Completion signal — polling, with callbacks as a wake-early optimization.** The orchestrator always polls (`query_run_status`, `get_approval_status`): async waits set the run's `scheduled_at` a poll interval into the future, and a worker re-drives the run when due. **Callbacks co-exist with polling** to cut that wait: an external system (the ticket system on an approval change, the engine on run completion) POSTs to `/api/v1/callbacks/{ticket-approval,engine-run}` with only a *neutral reference* (`ticket_id` / `engine_run_id`), and the orchestrator resolves the waiting run and sets `scheduled_at=now` (`runs.wake(...)`) so it re-polls immediately. The callback **never carries a status** and is not a run-store writer of state — the re-driven poll step still reads the authoritative external status, so polling remains the source of truth and a lost/duplicate/out-of-order callback is harmless (the run advances on its next poll anyway). Auth is **network-trust** (no HMAC/token); the endpoints are idempotent (a stale or unknown reference is a no-op, `woken=0`). *The ServiceNow side (a business rule POSTing `ticket_id` on approval) is configured in ServiceNow; the Airflow side is a best-effort `on_success/on_failure_callback` on the DAG (`notify_orchestrator` in `airflow/dags/cloudio_callbacks.py`).*
> 3. **Reference fields carry sys_ids.** Teams and users travel through the orchestrator as **names**, and the ServiceNow adapter resolves each to a sys_id before writing it. There are **two independent group inputs, one per ticket type, and they never feed each other**: the **`approval_group` catalog variable** inside the trigger's `ticket_params` names the team whose approval the **RITM** needs, while the `responsible_group` a failing DAG publishes in its exception XCom routes the **incident**. Resolution for both: the `servicenow_responsible_groups` map first, then `sys_user_group` by name (remembered for the life of the process); `caller_id` / `sysparm_requested_for` come from `sys_user`. A group name that resolves nowhere is never written into a *reference field* — an Incident falls back to the default `cloudio` team and, failing that, opens unassigned for ServiceNow to triage. The `approval_group` variable is the exception: it is a caller-supplied catalog variable, so an unresolved name is ordered exactly as it came rather than being silently dropped. *The variable name must match the catalog item's own variable, or ServiceNow discards it without complaint.* A user that resolves nowhere does fall back to the raw login, which ServiceNow accepts. *The columns those lookups match on are `GROUP_LOOKUP_FIELD` (`sys_user_group.name`) and `USER_LOOKUP_FIELD` (`sys_user.user_param`) in `adapters/servicenow.py` — change them there if your instance identifies groups or users by something else.*
> 4. **A DAG-run `success` is not proof of success.** A DAG with a rollback branch rolls each failed task back, and once the rollbacks succeed **Airflow marks the run `success`** — so the run state alone cannot tell a fulfilled run from an undone one. The rollback controller publishes two XComs the orchestrator treats as contract: **`flow_failed`** (true when one or more tasks failed) and **`failed_tasks`** (`{task_id: responsible_group}`). A `success` run is reported as an engine **failure** whenever `flow_failed` is true, and the incident is raised for the *first* entry of `failed_tasks` — one run, one incident, even when several groups own failures. The failed task instances stay in state `failed` and still publish their `exception_type` XCom, so the message and the classification below are unaffected. A DAG without a rollback branch publishes neither key and is unaffected: absent reads as false.
> 5. **Failure model.** **The DAG decides what its failure costs the requester**, by which exception it raises. A task-level `on_failure_callback` publishes `{message, exception, responsible_group}` to the `exception_type` XCom the orchestrator reads back (`exception_callback(...)` in `airflow/dags/cloudio_callbacks.py`), and the orchestrator classifies the failure by the *exception class name* — the payload has no other room, so the three names are a contract: <ul><li>**`ValidationException`** — the request is invalid. **No Incident**, not retried; the RITM is closed *unsuccessful* with "Your request was closed due to a validation error".</li><li>**`InfraPrecheckException`** — a precheck refused it. Handled identically to a validation failure.</li><li>**`TaskException`** (and anything unrecognised) — the work broke. Retried first (per-step backoff via `scheduled_at`); once exhausted a ServiceNow **Incident** opens to the `responsible_group` the DAG named (else the default `cloudio` team), titled `Error in {workflow name} automation ({RITM})` (the registered workflow's name, falling back to its identifier; the RITM is omitted when the run failed before opening one) and carrying `Run {run_id} has failed with the following error: {exception message}` as both its description and a work note, and the RITM is closed *unsuccessful* with "An error occurred. Incident {incident_id} was created".</li></ul>A failure raised **outside** the engine gets the older treatment: Incident to the default `cloudio` team, work note on the RITM, RITM left open. That covers everything else that can go wrong while a run is driven — a provider call exhausting its retries, a step deadline, and any exception in the driving code itself (an unknown step, a missing handler, a failing save), which ends the run `FAILED` on the first occurrence rather than being re-driven forever. The one exception is a **rejection**: an approver denying the RITM ends the run `REJECTED` with no Incident, since the RITM already records it. Either way the run terminates as `FAILED` and **there is no rollback** — a resource created before a later step failed is left exactly as it was, still marked `in_progress=True` (only `FinalizeResourceStep` clears that, and a failed run never reaches it), for operator follow-up. *An unsuccessful close is RITM state 4 (Closed Incomplete) — confirm that code matches your instance.*
