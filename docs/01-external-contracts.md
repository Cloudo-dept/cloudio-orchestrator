# User Review Required

> [!IMPORTANT]
> **Contracts on external services:**
> 1. **Idempotency keys.** Run delivery is at-least-once (a worker can crash mid-call, or a run can be re-driven by another worker after its lease expires during a slow call). Every side-effecting external call carries a per-attempt idempotency key `(run_id, step, attempt)`. **Airflow** sends it as the `dag_run_id` (a duplicate returns HTTP 409, treated as "already triggered"). **ServiceNow** Create Request has no native idempotency key, so the orchestrator looks up an RITM tagged with `correlation_id == key` before ordering and tags the new RITM after (residual window: a crash between ordering and tagging could double-order within one attempt; the per-attempt key bounds it — note that with compensation removed a double-ordered RITM is *not* auto-annotated, so this window is now operator-visible only). **Project Manager** Create Resource is effectively keyed by the caller-supplied `vendor_id` (plus an orchestrator-added `Idempotency-Key` header). *Confirm each service actually honors these.*
> 2. **Completion signal — polling only.** Airflow has no native outbound webhook, so the orchestrator polls (`query_run_status`): async waits set the run's `scheduled_at` a poll interval into the future, and a worker re-drives the run when due. *A webhook callback was deliberately dropped from this revision* — it added a route, an HMAC secret, and a second concurrent writer to the run store while polling remained the authoritative driver anyway. If an engine that can call back ever needs lower latency, a callback endpoint can be reintroduced as a pure optimization: it would only set `scheduled_at=now` to wake the run early; the model doesn't change.
> 3. **Failure model.** On a step's permanent failure the orchestrator opens a ServiceNow **Incident** to the responsible group (from Airflow *Get Task Exceptions* for DAG failures, else the default `cloudio` team), adds a work note to the corresponding RITM, and terminates the run as `FAILED`. Transient errors are retried first (per-step backoff, scheduled via `scheduled_at`); the Incident opens once retries are exhausted. **There is no rollback** — a resource created before a later step failed is left with `in_progress=False` for operator follow-up. *If you want DAG failures to skip retries and escalate immediately, set the run's `max_retries=0`.*
